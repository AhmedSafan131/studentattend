# سياسة اكتشاف Brave لبوابة الطالب

تاريخ التنفيذ: 1 نوفمبر 2026. السياسة تخص الحساب الذي يثبت السيرفر أن دوره `student`، أو زيارة مسار بوابة الطالب المنفصل قبل الدخول. ليست حظرًا عامًا للمتصفح، وليست بديلًا عن صلاحيات أو تحقق تسجيل الحضور على السيرفر.

## التحكم

المفتاح المركزي `blockBraveForStudents` داخل إعداد `student_login_options` الموجود في `system_settings`. يظهر في إعدادات دخول الطلاب داخل شاشة إعدادات الأدمن بعنوان «حظر Brave لبوابة الطالب فقط». يستخدم نفس صلاحيات إدارة إعدادات دخول الطلاب الحالية ونفس إبطال الكاش عند الحفظ. لا توجد migration جديدة ولا تغيير لبيانات الحضور أو ربط الأجهزة.

القيمة الافتراضية في الكود `false` للتوافق مع النسخ الحالية. تم تفعيل المفتاح في نسخة Docker المحلية أثناء تطبيق التغيير بعد نجاح الاختبارات؛ التعطيل من شاشة الأدمن يعيد التدفق الطبيعي، دون حذف بيانات.

## المسارات المشمولة

- `/student` و`/student/history` و`/student/profile` وكل `/student/*`، في تخطيطي الديسكتوب والموبايل، بما فيها الدخول المباشر وإعادة التحميل.
- صفحة الدخول المشتركة `/` تبقى متاحة. بعد التحقق من بيانات الدخول في السيرفر، يمنع سياق الطالب المكتشف، وتستمر حسابات `staff` و`doctor` و`admin`.
- طلبات الطالب الموثقة المارة بـ`auth.token` كلها، بما فيها المسارات المشتركة: `/api/auth/me`، `/api/attendance/my`، `/api/attendance/scan`، `/api/attendance/scan-status`، `/api/attendance/server-time`، `/api/terms` ومسارات الكتالوج. لا يتخذ القرار من اسم الرابط أو الدور المرسل وحده.
- `/api/auth/login` قبل ربط الجهاز وإصدار التوكينات وتحميل التسجيلات؛ `/api/auth/refresh` بعد التحقق من صاحب جلسة التجديد وقبل تدويرها؛ `/api/auth/upgrade-student-session` من خلال المصادقة الموثقة.
- تسجيل الخروج يبقى متاحًا حتى عند الحظر.

المشروع يخزن دورًا واحدًا للحساب في `users.role`. يتعامل `Role` مع `doctor` كمرادف لـ`staff`، وتوجد قراءة متوافقة مع بيانات `doctor` القديمة. لم يُضف نظام جديد للحسابات متعددة الأدوار. عند وجود Bearer صالح لموظف وcookie قديمة لطالب، تحدد هوية الـBearer سياق الحساب الحالي وتظل جلسة الموظف مسموحة.

## التنفيذ

1. `StudentBrowserPolicy` يفحص العلامة الإيجابية في `Sec-CH-UA` أو `User-Agent`، ثم يطبق المنع فقط على هوية `student` الموثوقة. الرد `403` مع `errorCode: STUDENT_BROWSER_BLOCKED` والرسالة المحددة، دون بيانات الطالب. غياب العلامات لا يثبت نوع المتصفح.
2. الواجهة تفحص `navigator.brave.isBrave()` بمهلة محدودة، وعلامات العلامة التجارية المتاحة. النتائج تشمل اكتشافًا إيجابيًا، عدم اكتشاف، أو حالة غير محسومة؛ عدم الدعم أو الخطأ لا يصنف كل المتصفحات Brave. لا يلغي فحص لاحق سلبي أو غير محسوم اكتشافًا إيجابيًا سابقًا داخل نفس مستند المتصفح.
3. `StudentBrowserBoundary` قبل `StudentPwaProvider` و`AppProviders`، فتسبق استعادة الجلسة، قراءة بيانات الطالب، تركيب الطالب والاسكانر والكاميرا، إنشاء السوكيت والمزامنة. عند الحظر اللاحق من السيرفر تُزال المكونات العاملة. إعادة الفحص عند التركيز أو عودة الاتصال تتم دون إعادة تركيب تطبيق الموظف المسموح.
4. `/api/student-browser-policy` يعيد إعداد السياسة وإشارة اكتشاف السيرفر فقط. `/api/auth/session-context` يعيد الدور فقط بعد قراءة Bearer أو cookie تجديد صالحة، دون تدوير cookie أو إرجاع ملف شخصي. تستخدم الواجهة التوكين المحلي كبيانات اعتماد للتحقق، ولا تستخدم الدور المحلي كحقيقة.
5. إذا ظهر Brave في JavaScript وحده على صفحة الدخول المشتركة، تستخدم الواجهة `/api/auth/credential-context` للتحقق من بيانات الدخول والحصول على الدور فقط، دون توكين أو cookie أو ملف طالب أو تعديل بصمة جهاز. تتوقف قبل طلب الدخول الكامل إذا أكد السيرفر سياق الطالب. نقطة التحقق المصغرة محدودة بمعدل طلبات، ولا تمنح تصريحًا أو شهادة بأن المتصفح مسموح.
6. لا توجد قيمة `isBrave=false` أو هيدر مخصص أو cookie شهادة أو توكين «متصفح مسموح». لا يثق السيرفر في نتيجة JavaScript لتجاوز فحصه المستقل. الحظر المحلي في Axios لمنع استمرار الوظائف هو تنظيم للواجهة، وليس تفويضًا أمنيًا.

رسالة الحظر:

> تم حظر هذا المتصفح. برجاء الدخول باستخدام الشورت كت أو Google Chrome أو Safari.
>
> شكرًا لتفهمكم.
> إدارة تكنولوجيا المعلومات — جامعة المنوفية الأهلية.

تعديل الصياغة لا يغير نطاق السياسة: الشورت كت المبني على Brave يظل خاضعًا لنفس اكتشاف المتصفح والحظر.

## العمل دون اتصال والبيانات المحفوظة

- يحتفظ IndexedDB/طابور الحضور بكل التسجيلات المعلقة. `STUDENT_BROWSER_BLOCKED` ليس رفضًا دائمًا لصحة إثبات الحضور، ولا يؤدي إلى حذفه أو متابعة بقية الدفعة. يتوقف إرسال المسح والاستعلام عن تأكيده عند الحظر.
- تخزن الواجهة آخر قيمة معروفة لإعداد السياسة لاستخدامها عند انقطاع الاتصال. هذه ليست شهادة سماح، ولا تُرسل للسيرفر كدليل على المتصفح أو الدور. مسار الطالب المنفصل يمكن حظره بالسياسة المحفوظة والاكتشاف الإيجابي حتى مع تعذر استعلام الهوية.
- فشل التحقق من هوية حساب محتمل على صفحة مشتركة/لوحة التحكم يعطي شاشة خطأ محايدة وإعادة محاولة، ولا يصنفه طالبًا أو Brave. لا توجد شاشة انتظار غير محدودة؛ لفحوص المتصفح والطلبات مهل محددة.
- لا تُمسح بيانات الحضور عند تحديث Service Worker. ارتفع إصدار كاش التطبيق من v3 إلى v4 لتحديث ملفات الواجهة، وبيانات IndexedDB منفصلة عن كاش ملفات التطبيق. الـService Worker لا يخزن استجابات `/api/`.
- الحضور المعلق داخل Brave لا ينتقل تلقائيًا إلى Chrome/Edge/Safari؛ قد يحتاج تسوية إدارية أو تعطيل السياسة مؤقتًا لمزامنته. لا تُحذف إثباتاته بواسطة هذه الميزة، لكن تظل شروط قبول الإثبات ومدته لدى السيرفر كما هي.
- ربط الجهاز وبصمته لم يتغيرا. انتقال طالب مرتبط سابقًا بـBrave إلى متصفح آخر يمر بحماية الجهاز الحالية؛ إذا لم تتطابق البصمة بما يكفي قد يحتاج إعادة ضبط الربط بالطريقة الإدارية الحالية. لا يُفك ربط الحساب تلقائيًا بسبب الحظر.
- نسخة قديمة مخزنة بالكامل دون اتصال لا يمكن فرض تحديث كودها أو أحدث إعداد عليها قبل وصول التحديث/الاتصال. الصفحات القديمة المفتوحة قبل النشر قد تحتاج إعادة تحميل. السيرفر يطبق السياسة على الطلبات المكتشفة عند وصولها.

## الحدود

- يمكن إخفاء علامات المتصفح أو التلاعب بـJavaScript أو الطلبات المباشرة. غياب جميع العلامات قد يتجاوز الاكتشاف. الحل ليس ضمانًا 100%، ولا يمنع طالبًا من استخدام متصفح آخر مسموح.
- لم يتغير خادم Socket.IO: الواجهة المحظورة لا تنشئ اتصالًا. الخادم الحالي يستخدم `clientType` غير موثق، ولذلك لا يُستخدم لتحديد الدور أو حظر اتصالات مباشرة باعتبارها طالبًا. توثيق اتصالات الخادم المباشرة موضوع منفصل كما تم الاتفاق قبل التنفيذ.
- لم تُجر تجربة أجهزة iOS/Safari/Edge حقيقية. توجد اختبارات لوكيل المستخدم وعدم دعم API أو خطئه، واختبارات فعلية لـBrave وChrome على Windows بوضع headless.
- تحذيرات البناء السابقة الخاصة بحجم الحزمة وBrowserslist ومتغير غير مستخدم في صفحة المواد بقيت كما هي. لم تُغيّر هذه المهمة إعدادات الدخول الأخرى أو حماية تسجيل الحضور.

## ما تم اختباره

- المجموعة الكاملة للباك إند: 126 اختبارًا و1174 تحققًا ناجحًا. تشمل اختبارات جديدة للطالب على Brave، الطلبات المباشرة، منع إصدار التوكين أو تعديل الجهاز، منع تدوير cookie، تجاهل علامة سماح مزعومة، أدوار غير الطالب، سياسة معطلة، هويات مجهولة، ومراعاة هوية الموظف عند وجود cookie طالب قديمة.
- المجموعة الكاملة للواجهة: 151 اختبارًا في 26 مجموعة، وفحص ESLint وبناء الإنتاج المحلي وبناء Docker ناجحة. تشمل اختبارات البوابة والروابط المباشرة، عدم تركيب وظائف الطالب، الدور المحلي المزوّر، الدخول المشترك، استمرار الأدوار الأخرى، عدم إعادة تركيب التطبيق عند التركيز، خطأ الفحص، انقطاع الاتصال، والحفاظ على الطابور.
- اختبارات متصفح بقاعدة SQLite مؤقتة وحسابات تجريبية فقط: Brave حقيقي لطالب مسجل، إعادة تحميل، cookie طالب مع دور محلي مزوّر، محاضر على Brave، طالب على Chrome، اكتشاف JavaScript وحده، رابط طالب دون تسجيل الدخول، وصفحة دخول مشتركة وتقديم بيانات دخول طالب. تم رصد طلبات الشبكة واتصالات WebSocket والتأكد من عدم بدء وظائف الطالب المحظور، وعدم ظهور أخطاء JavaScript.
- أداة المتصفح المحلية وبياناتها المعزولة موجودة في `D:\student-attendance\.attendance-audit\browser-policy-smoke.cjs` و`browser-policy-init.php`. ملفات التعريف وقواعد بيانات التجربة مؤقتة ومنفصلة عن قاعدة التشغيل.
- بعد تشغيل الصورة النهائية وتفعيل المفتاح، نجح اختبار Brave حقيقي بملف متصفح جديد على Docker المحلي: `/student/history` محظور قبل طلب بيانات الطالب، إعادة التحميل محظورة، و`/` يعرض صفحة الدخول المشتركة. لا توجد أخطاء JavaScript. هذه التجربة لم تستخدم بيانات اعتماد أو تعدّل سجلات حضور على قاعدة التشغيل. أداة التحقق `browser-policy-live.cjs`.
